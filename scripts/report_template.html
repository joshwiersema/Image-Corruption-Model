What a broken frame actually looks like

Nobody had a library of glitched game frames to learn from, so the project makes its own. It takes a clean frame and damages it in six ways that each imitate a real hardware failure, with a severity dial from 0.2 (barely visible) to 1.0 (catastrophic). Because the program chose the damage, it already knows the right answer — that is where the training labels come from.

What it learned from, and whether it finished

Training is a loop: guess, be told the answer, nudge 1.2 million internal numbers slightly towards being right, repeat. Two things about this particular run are worth seeing. The diet was lopsided — a third of everything it saw was labelled clean — and the run was stopped while it was still getting better.

What it gets right

The grid below is a confusion matrix: every row is what a frame really was, every column is what the model called it. Correct answers land on the diagonal; everything off it is a mistake, and which mistake matters. Confusing two faults with each other is a triage problem. Confusing a fault with clean means a broken frame shipped as fine — the one error that actually costs something.

Where it goes blind — and one fault it cannot win

A single accuracy number hides everything interesting. Split the same model by how severe the damage was and the picture changes completely: three faults are caught perfectly at every strength, and two fall apart at the quiet end where catching them would matter most.

Would real pictures be better?

Two different things here are synthetic, and only one of them has to be. The damage is generated in code by necessity — that is where the labels come from, and no library of pre-labelled glitched frames exists. The clean frames underneath are drawn in code purely so the project runs with nothing to download. To test whether that second choice costs anything, the same checkpoint was pointed at 24 real photographs it had never seen, with the identical faults injected.

Diagnosis

It partly learned the generator, not the fault

A torn frame is only visible as a displacement of something recognisable. In a drawn scene of flat colour blocks, sliding a band sideways leaves an obvious step. In a photograph full of natural texture, the same slide hides in the noise. The detector had been rewarded for spotting “a discontinuity in flat colour” — a property of the drawing program, not of the hardware fault. Note which two faults this hits: the same two that were already weakest.

So we went and got real ones

The drawn frames have been replaced with 1,550 real game captures pulled from ten titles — Among Us, Apex Legends, Fortnite, Forza Horizon, Free Fire, Genshin Impact, God of War, Minecraft, Roblox and Terraria. That is thirteen times the source material, and far more importantly it is thirteen times more varied: real lighting, HUD overlays, UI text, aliasing, compression and ten completely different art directions.

Prediction, not yet a result

Real frames may partly heal the channel-swap flaw on their own

A full-frame colour swap was unlearnable on drawn scenes because those scenes were generated with random palettes — any colour was as plausible as any other. Real game frames carry strong colour expectations: sky is blue, grass is green. Swapping the channels of a real frame turns the sky magenta, which is evidence. The retrain will show whether the network picks that up.

What the audit found

Twenty-one checks over the fault injectors, the data pipeline, the saved model and the evaluation path. Nineteen pass. The two failures are both real, and neither is in the network — they are in the scaffolding around it.

Contradictory labels · corruption.py

A full-frame channel swap is indistinguishable from a clean frame

At severity 1.0 the affected region grows to cover the whole image, so the “fault” leaves no evidence behind. Detection collapses to essentially zero. Every one of those samples teaches the network something false, and drags the honest cases down with it.

Silent mismatch · evaluate.py

Scoring uses a different mix of frames than training did

The evaluator rebuilds its test set from built-in defaults rather than from the recipe stored in the checkpoint, so it grades with 35% clean frames against a model trained on 30%. Today the numbers are close enough to be believable; change a training setting and the score silently stops describing the model you trained.

Imbalance · dataset.py

One class is 2.4× more common than the rest

“Clean” dominates the training diet, which biases every uncertain decision toward it — visible as the two heavy cells in the leftmost column of the confusion matrix.

Verified · 19 checks

The parts that hold up

Every injector returns a new, valid, genuinely-changed frame and rejects malformed input rather than guessing. No source frame leaks between the training and test sets. The two labels always agree. The test set is reproducible frame-for-frame. The checkpoint rebuilds its own architecture without being told.

What to fix, in order

Ranked by what buys the most accuracy per hour spent. The first three are small, contained edits; the last two are the difference between a demo and something that could watch a real driver.

Stop generating unlearnable channel swaps

Cap the affected region below the full frame so a boundary always survives — one constant in corruption.py. Removes a whole class of self-contradicting training examples.

1 linehigh impact

Even out the classes

Drop the clean share to roughly one in seven, or weight the loss so a rare fault counts for more than a common clean frame. Directly attacks the “when unsure, say clean” bias.

smallhigh impact

Make the evaluator read the checkpoint's recipe

Pull clean_ratio and the severity range from the saved settings the same way the architecture already is. Correctness, not accuracy — it stops the score from quietly lying later.

smallcorrectness

Train longer, at full resolution

The accuracy curve had not flattened at eight epochs, and 128×128 throws away exactly the fine detail that separates a smear from motion blur. Try 30 epochs at 256×256.

compute-boundhigh impact

Report accuracy by severity, not one number

Every chart in section 04 exists because the headline number hid the answer. Bin the evaluation the same way so a regression at low severity cannot hide behind a good average.

mediumvisibility

Teach the smear-versus-blur distinction explicitly

Add motion blur, bloom and depth-of-field to the clean side. Right now nothing in the training data says these are acceptable, so the model has no reason to learn the line between them.

mediumhigh impact

Use real captured frames

Measured cost of not doing this: detection falls 90% → 74% on pictures from outside the generator, and tear detection loses two thirds of its accuracy. Point --clean-dir at a folder of real captured frames — the pipeline already accepts them unchanged.

largehigh impact

Ship an inference path and a test suite

There is still no way to hand this program a single screenshot and get an answer, and no automated tests guarding any of the invariants the audit checked by hand.
