Automated GPU render-artifact detection · technical evaluation

Real Frame
Retrain

Detecting image corruption today means a human watching a screen. This is a 1.2M-parameter network that judges a rendered frame in about 10 ms — whether it is corrupted, and which fault it is. Retraining it on 1,550 real game captures instead of synthetic scenes took naming accuracy on real frames from 68% to 95%, and false alarms on clean frames from 23% to zero.

The head-to-head

Both models judged on the same 310 held-out real frames, with the same faults at the same seeded severities. The only variable is what each one learned from. This is the comparison that matters, because real frames are what a detector would actually meet.

The operationally decisive number

False alarms went from one in four to zero

The old model called 23% of perfectly good game frames “broken”. The new one called none of them broken — 388 clean frames, 388 correct. For a detector meant to run unattended across a test farm, that matters more than the naming accuracy: a tool that cries wolf on a quarter of its input is a tool people switch off.

What changed: the frames

The old source set was twelve procedurally drawn scenes — checkerboards, brick walls, gradients. The new one is 1,550 captures from Among Us, Apex Legends, Fortnite, Forza Horizon, Free Fire, Genshin Impact, God of War, Minecraft, Roblox and Terraria. Thirteen times the material, and far more importantly thirteen times more varied.

What it gets right now

Sixteen epochs, and unlike the previous run this one actually finished — the curve flattened around epoch 13 rather than still climbing when the budget ran out.

A hypothesis rejected, and the defect it exposed

One outcome was predicted in advance and did not hold. The expectation was that real frames would fix the full-severity channel-swap failure on their own: a full-frame colour swap is unlearnable on procedural scenes because those scenes carry random palettes, so magenta sky is as plausible as blue. Real games carry strong colour expectations, so a swapped frame should look wrong. It is a reasonable argument, and the measurement rejected it — which turned out to be the more useful result, because it located the defect precisely.

Root cause · found and closed

The fault generator was producing samples that could not be learned

Better frames lifted channel-swap accuracy everywhere except at full severity, where detection stayed at 5%. The cause was in the fault generator, not the network: at severity 1.0 it swapped the colour channels of the entire frame, leaving no boundary and no correctly-coloured reference. Such a sample is labelled corrupted while being identical in kind to a clean one. Capping the affected region at 85% of each axis guarantees a visible boundary survives. Detection at full severity went 5% → 88%.

What this means

The network was never the problem

The 5% → 88% jump was measured on the existing model with no retraining at all: the change was to the data definition alone. The network had always known how to recognise a channel swap; it had been shown impossible examples and marked wrong for failing them. A full retrain on the corrected data afterwards moved overall accuracy by 0.0 points, which confirms it. Two distinct failure modes were at work — learning the wrong cue, which better data fixed, and an unlearnable label, which only a definition change could fix.

What is left

The data problem is solved and the one correctness defect is closed. What remains is a perception limit, two small code changes, and one honest boundary on what any of this proves.

Teach faint smear against real motion blur

The one remaining weak spot, and a perception limit rather than a defect: texture_smear at severity 0.2 is caught 50% of the time, because a mild smear and ordinary motion blur genuinely look alike. Real game frames already contain motion blur, so the distinction can now be taught with labels rather than invented.

mediumlast weak spot

Make the evaluator inherit the checkpoint's recipe

evaluate.py rebuilds its test set from module defaults rather than the settings stored in the checkpoint, so a scoring run can silently describe a different data distribution than the one the model was trained on. Encountered three times during this evaluation.

smallcorrectness

Even out the classes

Clean is still over-represented at roughly 2.4×. Less urgent now that false alarms are at zero, but it is free accuracy on the two weak faults.

smalltidy-up

Remember what this still is not

The frames are real. The damage is not — it is injected in software, because no labelled corpus of genuine GPU artifacts exists. Validating against actual failing hardware remains the one thing none of this proves.

Reproducing these results

Every figure and number on this page regenerates from these five commands. Frames download in about two minutes; the retrain is 55 minutes on CPU, no GPU required.

python scripts/fetch_game_frames.py Downloads the game captures into data/game_frames and records their source.
python -m src.train --clean-dir data/game_frames --epochs 16 --image-size 160 \ --samples-per-image 4 --batch-size 64 --lr 1e-3 --checkpoint-dir checkpoints/pretrained The exact run behind this page.
python scripts/compare_models.py --baseline <drawn-frame checkpoint> --candidate checkpoints/pretrained/best.pt Reproduces the head-to-head table and chart in section 01.
python scripts/live_view.py --checkpoint checkpoints/pretrained/best.pt Opens the live window at the top of this page.
python scripts/make_visuals.py --checkpoint checkpoints/pretrained/best.pt --source-dir data/game_frames Rebuilds every figure here from the new checkpoint.
Measured on the epoch-16 checkpoint at 160×160, CPU inference, 1,240 held-out samples, and a 310-frame head-to-head against the previous model. Frames from the Bingsu/Gameplay_Images dataset, CC-BY-4.0. Every number and figure was generated from those checkpoints, not estimated.
